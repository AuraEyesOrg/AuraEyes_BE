# Scheduling Quota Manual Test Guide (Backend + UI)

## Purpose
This guide verifies that part-time quota enforcement and full-time auto-generation work correctly across backend APIs and system-admin UI.

## Preconditions
- Backend migrated with quota migration:
  - dotnet ef database update --project src/Infrastructure --startup-project src/API
- API is running.
- Frontend is running.
- You have a System Admin account and at least:
  - 1 part-time ophthalmologist
  - 1 full-time ophthalmologist

## Recommended test settings
Set these keys in System Settings:
- PART_TIME_MAX_SLOTS_PER_DAY = 5
- FULLTIME_SLOT_WINDOW_DAYS = 7

This makes quota behavior easier to observe.

## A. Backend manual tests

### A1. Part-time single create respects quota
1. Create slots for a part-time doctor on date D until total used reaches 5.
2. Try to create one more slot on date D.
Expected:
- First 5 slot creations succeed.
- Next creation fails with quota-related business message.
- No extra slot is inserted.

### A2. Part-time bulk generate reserves before insert
1. Submit GenerateSlots request for part-time template that would create N slots on same date D.
2. Ensure N is less than or equal to remaining quota, verify success.
3. Submit another bulk request that exceeds remaining quota.
Expected:
- Request exceeding remaining quota is rejected.
- Database remains consistent (no partial over-quota insert for date D).

### A3. Race-condition safety under parallel requests
1. Keep PART_TIME_MAX_SLOTS_PER_DAY = 5.
2. Fire 10 parallel create-slot requests targeting same date D (distinct time ranges).
Expected:
- At most 5 requests succeed.
- Remaining requests fail gracefully.
- Final used count for D is exactly 5 (never > 5).

### A4. Full-time manual operations are blocked
1. Use full-time doctor account/context.
2. Call manual CreateAppointmentSlot endpoint.
3. Call GenerateSlots endpoint.
Expected:
- Both are rejected by business rule.

### A5. Full-time rolling window generation
1. Ensure there is an active full-time schedule template.
2. Trigger/await recurring job execution.
3. Check slots generated from today to today + FULLTIME_SLOT_WINDOW_DAYS.
Expected:
- Missing future days are generated by system.
- Existing generated slots are not duplicated.

### A6. Admin usage endpoint
1. Call GET api/system-admin/dashboard/part-time-slot-usage?fromDate=YYYY-MM-DD&toDate=YYYY-MM-DD
Expected:
- Returns row per day in range.
- Each row has date, usedSlots, quota, remainingSlots.
- Days without row in DailySlotQuotas still return defaults from configured quota.

## B. UI manual tests (System Admin)

### B1. Dashboard quota usage widget
Page:
- /system-admin/dashboard

Steps:
1. Open Part-time slot quota usage section.
2. Change range with date pickers and 7d/14d/30d presets.
3. Compare chart values with backend API response for same date range.
Expected:
- Chart loads and updates per selected range.
- Summary cards reflect totals and utilization.
- Error state appears if API fails.

### B2. Export dashboard includes quota rows
1. On dashboard, click Export Excel.
2. Open exported file.
Expected:
- Contains rows in section Part-time slot quota usage.
- Row format includes date and used/quota/remaining values.

### B3. Settings update for quota/window keys
Page:
- /system-admin/settings

Steps:
1. Update Part-time max slots per day.
2. Update Full-time generation window (days).
3. Save changes.
4. Refresh page.
Expected:
- New values are persisted and reloaded.
- Subsequent dashboard usage endpoint reflects updated quota defaults for untouched days.

## C. Data consistency checklist
After tests, verify:
- No day exceeds configured part-time quota.
- DailySlotQuotas table values match effective slot allocations.
- No duplicate system-generated full-time slots for same template/date/time.

## D. Troubleshooting
- If dashboard usage looks empty:
  - Confirm date range and timezone expectations.
  - Confirm system-admin authorization token and endpoint accessibility.
- If quota appears unchanged:
  - Re-check system settings save success.
  - Verify API instance uses updated settings source.
- If parallel test is flaky:
  - Increase parallel requests and repeat.
  - Check server logs for reservation conflicts and retries.
